# 26 — Router y `kai-build`: apps como árbol de carpetas

**Estado:** propuesta (24-oct-2026), no implementada. Reemplaza el diseño de
rutas de [09 §7](09-framework-y-plataforma.md#7-rutas-y-ventanas) y concreta
el Paso 22 de [13](13-hoja-de-ruta-plataforma.md). Plugins (Paso 25) quedan
fuera: se retoman después.

**Norma:** todo concepto de código va en inglés (tipos, funciones, módulos,
archivos, carpetas, variantes, ids de comando). Solo el texto que ve la
persona usuaria puede ir en español.

## 1. Objetivo

Una app Kai deja de ser un solo `App` con un `update` gigante. Su estructura
de carpetas define sus secciones, sus rutas y su barra lateral:

```
my-app/
  kai.toml
  build.rs                  ← kai_build::generate()
  src/
    main.rs                 ← kai::include_app!(); fn main() { app::run() }
    state.rs                ← estado compartido (sesión, usuario, datos)
    sections/               ← cada carpeta: una entrada de la barra lateral
      customers/
        section.rs          ← título, icono, orden, grupo (lo que se ve)
        page.rs             ← ruta /customers
        [id]/
          page.rs           ← ruta /customers/:id (no va en la barra)
      sales/
        section.rs
        page.rs
    windows/                ← reservado para el Paso 23 (varias ventanas)
```

- **Convención con salida:** `kai new` crea esta estructura y `kai doctor` la
  valida, pero todo lo que genera `kai-build` también se puede escribir a
  mano con los mismos traits. Ningún caso raro queda bloqueado.
- **La barra lateral refleja el árbol, no lo copia:** el primer nivel de
  `sections/` da las entradas; `section.rs` decide título (en español si se
  quiere), icono, orden y grupo. Las subrutas no aparecen en la barra.

## 2. Requisito previo: `Element::map` y `Effects::map`

Cada página tiene su propio `Msg`. Para componerlas en una raíz hace falta
convertir un `Element<PageMsg>` en `Element<RootMsg>` y lo mismo con los
efectos. Hoy no existe.

```rust
impl<Msg: 'static> Element<Msg> {
    pub fn map<To: 'static>(self, f: impl Fn(Msg) -> To + Clone + 'static) -> Element<To>;
}
impl<Msg: 'static> Effects<Msg> {
    pub fn map<To: 'static>(self, f: impl Fn(Msg) -> To + Send + Clone + 'static) -> Effects<To>;
}
```

- `Element::map` recorre el árbol y envuelve cada handler (`on_click`,
  `on_input`, `on_select`, `on_drop_files`…; hoy son 10 campos en
  `Handlers`). Los mensajes guardados por valor se mapean al construir.
- `Effects::map` envuelve los `done` de `perform`/`after`; las claves de
  tareas (`keyed`) se prefijan con la ruta de la página para que dos páginas
  no se cancelen entre sí.
- **Costo:** se paga en cada `view`. Medido (`bench_element_map`, release):
  mapear la vista completa de una sección de la demo cuesta 10–27 µs (p50),
  7–12 % de construirla; una página real solo mapea su subárbol.

Es útil por sí solo (componentes con su propio `Msg`), así que va primero.

## 3. Contrato del router

### 3.1 `Route`

```rust
/// A place in the app. Generated by kai-build, or written by hand.
pub trait Route: Clone + Eq + std::fmt::Debug + 'static {
    /// `/customers/42` → `Customers42 { id: 42 }`; `None` if no route matches.
    fn parse(path: &str) -> Option<Self>;
    /// The inverse of `parse`: `parse(&r.path()) == Some(r)`.
    fn path(&self) -> String;
    /// Where "up" goes (detail → list); breadcrumbs follow it.
    fn parent(&self) -> Option<Self>;
    /// Sidebar entry this route belongs to (selected row), if any.
    fn section(&self) -> Option<usize>;
}
```

Decisiones:

- **Rutas como texto estable (`path`).** Sirve para persistir la última ruta
  ([`kai::store`](../../src/store.rs)), restaurar con `kai dev`, MCP
  (`kai.navigate` con un path), deep links más adelante y tests legibles.
  `parse` y `path` deben ser inversas; un test generado lo comprueba.
- **Sin `#[derive(Routable)]`.** 09 lo proponía; lo reemplaza la generación
  desde carpetas (§4). Escribir `Route` a mano sigue siendo posible.
- **Parámetros tipados.** `[id]` produce un campo cuyo tipo declara la página
  (`type Params`, con `FromStr` + `Display`). Un path con un id que no parsea
  es `None` (ruta no encontrada), no un panic.

### 3.2 `Router<R>`

Datos puros, en el modelo de la app, probado sin ventana:

```rust
pub struct Router<R: Route> { /* back stack, current, forward stack */ }

impl<R: Route> Router<R> {
    pub fn new(start: R) -> Self;
    pub fn current(&self) -> &R;
    pub fn push(&mut self, route: R);     // clears forward; no-op if equal to current
    pub fn replace(&mut self, route: R);  // no history entry
    pub fn back(&mut self) -> bool;
    pub fn forward(&mut self) -> bool;
    pub fn up(&mut self) -> bool;         // push(parent)
    pub fn can_go_back(&self) -> bool;
    pub fn can_go_forward(&self) -> bool;
}
```

- **Historial acotado** (100 entradas) para que una sesión larga no crezca
  sin límite.
- **La navegación es un `Msg`**, como todo en Elm: un clic, un atajo, un
  agente o un test pasan por `update`. La UI nunca cambia de ruta "por
  fuera".

### 3.3 Lo que aporta el runtime

El router es del modelo, pero hay comportamiento de ventana que no debe
escribir cada app. Para eso el runtime necesita leer la ruta:

```rust
trait App {
    /// Current route as a path, read after every update. Default: none.
    fn route(&self) -> Option<String> { None }
    // ...
}
```

Con la ruta, el runtime:

| Qué | Cómo |
|---|---|
| Scroll y foco por ruta | Guarda offsets y foco al salir de una ruta y los restaura al volver (atrás devuelve a donde estabas). El foco no se restaura si sigue en un control que está en las dos vistas (la fila de la barra lateral que se acaba de elegir). |
| Accesibilidad | Anuncia el título de la nueva vista (AccessKit). |
| Comandos | `kai.back` (⌘[), `kai.forward` (⌘]), `kai.up` (⌘↑), `kai.navigate { path }` para agentes; deshabilitados cuando no aplican (`can_go_back`). |
| Persistencia | La última ruta en el `Store` de la app, si la app lo pide. |
| Tests | `TestApp::navigate(path)` y `TestApp::route()`. |

**Implementado (R2):** el contrato quedó así en `src/router.rs`. Diferencias
con lo de arriba: `Route::section()` se deja para R3 (la barra lateral es de
las secciones); los comandos son `Action`s genéricas (`GoBack<A>`…) que la
app activa con `registry.navigation()` e implementando `Navigable`
(`nav_state()` y `navigate(Navigate) -> Msg`). Un path desconocido en
`kai.navigate` no cambia nada (no es error). Falta el anuncio a VoiceOver.

## 4. Páginas y secciones

### 4.1 `Page`

Una página es un pequeño `App` con parámetros y acceso al estado compartido:

```rust
pub trait Page: Sized + 'static {
    type Msg: Clone + std::fmt::Debug + 'static;
    /// What the route carries (`()` for /customers, `CustomerId` for /customers/:id).
    type Params: Clone + Eq + std::str::FromStr + std::fmt::Display + 'static;
    /// App-wide state the page reads and changes (src/state.rs).
    type State: 'static;

    fn init(params: &Self::Params, state: &Self::State) -> (Self, Effects<Self::Msg>);
    fn update(&mut self, msg: Self::Msg, cx: &mut Context<Self::State>) -> Effects<Self::Msg>;
    fn view(&self, state: &Self::State) -> Element<Self::Msg>;
    /// User-visible title (may be Spanish): window title, a11y announcement.
    fn title(&self, state: &Self::State) -> String;
}

/// What a page can do beyond its own model.
pub struct Context<'a, S> { /* &mut S, navigation requests */ }

impl<S> Context<'_, S> {
    pub fn state(&mut self) -> &mut S;
    pub fn navigate(&mut self, path: &str);   // checked by the root against Route::parse
    pub fn back(&mut self);
}
```

- **Estado compartido explícito** (`State`, de `src/state.rs`): datos que
  varias páginas usan (sesión, clientes cargados). Las páginas lo reciben,
  no lo duplican.
- **Navegar desde una página** pasa por `Context`, que la raíz convierte en
  un `Msg` de navegación. La página no conoce el enum `Route` completo; usa
  el path, que la raíz valida (un path inválido en debug es un panic con
  mensaje claro; en release, se ignora y se avisa).

### 4.2 Vida de una página

- **Secciones (primer nivel):** su página raíz se conserva al ir a otra
  sección y volver (filtros, selección, scroll intactos), como hace Mail o
  Finder.
- **Subrutas con parámetros** (`/customers/:id`): se crean al entrar y se
  descartan al salir; volver con ⌘[ las recrea con `init` (el scroll y foco
  los restaura el runtime, §3.3).
- Una página puede pedir lo contrario con una constante en su módulo
  (`pub const KEEP_ALIVE: bool`), sin cambiar el contrato.

### 4.3 `section.rs`

```rust
use kai::router::SectionMeta;
use kai::icons::Icon;

pub const SECTION: SectionMeta = SectionMeta {
    title: "Clientes",        // user-visible: Spanish is fine
    icon: Icon::Users,
    order: 10,
    group: Some("Datos"),     // sidebar group title
};
```

`kai-build` no evalúa Rust: solo genera código que referencia
`sections::customers::SECTION`. Si falta o tiene otro tipo, es un error de
compilación normal, con su línea.

### 4.4 Lo que enseñó la raíz escrita a mano (R3)

La raíz de `session/pages_tests.rs` ocupa ~150 líneas para dos secciones y
tres páginas: es exactamente lo que `kai-build` debe generar, y confirma que
nadie debería escribirla a mano. Cambios respecto de §4.1:

- `Page::Params` solo pide `Clone + Eq`: el parseo del path vive en
  `Route::parse` (el tipo del parámetro lo convierte la raíz), no en la
  página.
- La primera página se abre en `App::init`, para que corran sus efectos.
- Las páginas de sección se crean al primer uso y viven mientras corre la
  app; las de parámetros se crean al entrar y se descartan al salir de esa
  ruta, o al cambiar de parámetro.
- La raíz necesita, por ruta, el índice de su sección (fila elegida de la
  barra) y, por sección, el path de su página propia (clic en la barra).
  `kai-build` los saca del árbol de carpetas.
- `Context` junta pedidos de navegación; la raíz los aplica después del
  `update` de la página, junto con los efectos de abrir la página nueva.

## 5. `kai-build`

Crate nuevo del monorepo (`kai-build/`), dependencia de compilación de cada
app:

```toml
# my-app/Cargo.toml
[build-dependencies]
kai-build = { path = "../kai-ui/kai-build" }
```

```rust
// my-app/build.rs
fn main() {
    kai_build::app().generate().unwrap_or_else(|e| panic!("{e}"));
}
```

### 5.1 Qué lee

| Ruta | Significado |
|---|---|
| `src/sections/<name>/section.rs` | Una entrada de la barra lateral. Obligatorio por sección. |
| `src/sections/<name>/page.rs` | La página `/<name>`. |
| `src/sections/<name>/<seg>/page.rs` | Subruta fija `/<name>/<seg>`. |
| `src/sections/<name>/[param]/page.rs` | Subruta con parámetro `/<name>/:param`. |
| `src/state.rs` | Estado compartido (`pub struct State`). |
| `src/windows/<name>/` | Reservado (Paso 23): hoy, un aviso si existe. |

- Nombres de carpeta: `snake_case` en inglés (`customers`, `sales_report`);
  el path de la ruta usa `kebab-case` (`/sales-report`). Un nombre inválido
  es un error con la ruta del archivo.
- Carpetas con corchetes (`[id]`) no son nombres de módulo Rust válidos:
  el código generado usa `#[path = "…"] mod id_param;`, así la convención
  no depende de lo que acepte el compilador.
- Orden de la barra: `SectionMeta::order`, luego nombre. No depende del
  orden en que el sistema de archivos lista las carpetas, así la salida es
  determinista.

### 5.2 Qué genera

Un solo archivo, `$OUT_DIR/kai_app.rs`, que `kai::include_app!()` incluye:

- `enum Route` (una variante por página, con sus parámetros) e
  `impl kai::router::Route for Route`, más un test `parse(path(r)) == r` por
  variante.
- `struct AppRoot` con el `Router<Route>`, el `State`, las páginas vivas y
  `enum RootMsg` (una variante por página + navegación).
- `impl App for AppRoot`: reparte cada `RootMsg` a su página (`Effects::map`),
  arma la vista con la barra lateral (`Sidebar` desde los `SectionMeta`) y
  la página actual (`Element::map`), y publica `route()`.
- `pub fn run()`: abre la ventana con el tema de `kai.toml`.

El código generado es legible y formateado (`prettyplease`), para que
leerlo explique la app. No usa macros procedurales.

### 5.3 Buen comportamiento como build script

- `cargo:rerun-if-changed=src/sections` y `src/state.rs`, `src/windows`:
  solo regenera cuando cambia el árbol.
- Errores en español para la persona (es texto que ve), con la ruta del
  archivo y qué hacer: «Falta src/sections/customers/section.rs: cada
  sección necesita su SectionMeta».
- Sin red, sin escribir fuera de `OUT_DIR`.
- MSRV igual a Kai (1.95). Dependencias mínimas: `prettyplease` + `syn`
  (solo para formatear), sin `walkdir` (recorrido a mano).

### 5.4 Relación con la CLI

- `kai new <app>` crea `build.rs`, `state.rs` y una sección de ejemplo.
- `kai new section <name>` crea `section.rs` + `page.rs` con plantillas.
- `kai doctor` corre la misma validación que `kai-build` (comparten el
  módulo de escaneo: `kai-build` lo expone como `kai_build::scan`).
- `kai dev` ya observa `src/`: un cambio en el árbol regenera al compilar.

### 5.5 Convenciones fijadas al implementar (R4)

- Cada `page.rs` define **`pub struct Screen`** que implementa
  `kai::router::Page` (no `Page`: chocaría con el nombre del trait).
- Cada `section.rs` define **`pub const SECTION: SectionMeta`**.
- **Un parámetro por ruta** (`[id]`); su página declara `Params` con
  `FromStr + Display` (el código generado lo lee y lo escribe en el path).
  Varios parámetros (`/customers/[id]/invoices/[invoice]`) quedan para
  después (pregunta 3 de §7).
- Una ruta fija gana a un parámetro hermano: `/customers/new` no se lee
  como `[id] = "new"`.
- `kai::include_app!()` va en la raíz del crate (`main.rs` o `lib.rs`) y
  declara `state`, `sections` y `app`. `app::run(state, theme)` abre la
  ventana; `app::app(state)` da la app para `TestApp`.
- La app arranca en la primera sección de la barra (menor `order`).
- Sin `prettyplease` ni `syn`: el generador escribe el código ya
  formateado, y `kai-build` no tiene dependencias.
- Los módulos usan `#[path]` absoluto: el código generado vive en
  `OUT_DIR`. Un `mod helpers;` dentro de un `page.rs` se busca junto a él.

## 7. Preguntas abiertas

1. **¿Estado compartido único o por sección?** Propuesta: un `State` para
   toda la app (simple, como Elm). Si una sección necesita algo propio, lo
   guarda en su página.
2. **¿La raíz generada se puede extender?** Por ejemplo, una toolbar global
   o un `update` previo (autenticación). Propuesta: `src/app.rs` opcional
   con hooks (`fn shell(...)`, `fn before_update(...)`) que `kai-build` llama
   si existen.
3. **Rutas con varios parámetros** (`/customers/[id]/invoices/[invoice]`):
   el contrato lo permite; ¿hace falta en la primera versión? Propuesta: sí,
   cuesta poco en la generación.
